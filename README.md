# SakuraShop: PHP advisory-to-review fixture

Fictional Japanese SME storefront for the Arigato hackathon. **The checked-in baseline intentionally declares an affected PHP runtime. Do not deploy it.** All customers, orders and bearer tokens are public seeded fixtures. There are no external dependencies, API keys, payments, production endpoints or exploit payloads.

This repository supplies a reviewable target for ProofPatch. The backend orchestrator, live forum/X collection, Groq inference and automatic GitHub PR publisher are **not implemented here**. `demo/proposed-repair.patch` is a prepared, unapplied example; it was not generated by a running AI agent.

## What is real and what is replayed

The vendor advisories and candidate image metadata are real. Advisory delivery is a historical replay; the installed-version scenario is this synthetic repository inventory. PHP's October 21, 2026 advisories fix CVE-2026-109618 and CVE-2026-109619 in PHP 8.3.36. The October 23 notice retains a session-upload configuration follow-up. The prepared change updates runtime/constraint declarations and applies its startup setting; deployment and worker restart still need an owner. [PHP notices](https://www.php.net/archive/2026.php), [OOM advisory](https://github.com/php/php-src/security/advisories/GHSA-w8hw-w9fx-j79w), [stale-state advisory](https://github.com/php/php-src/security/advisories/GHSA-6wmf-4rv5-p3rp).

The reviewed candidate is `php:8.3.36-cli-bookworm` pinned to the Docker Hub index digest recorded in [demo/advisory.json](demo/advisory.json). Metadata was checked on October 24, 2026; no image was run during that research. Recheck the official registry before execution. [Registry metadata](https://hub.docker.com/v2/repositories/library/php/tags/8.3.36-cli-bookworm), [official image definitions](https://github.com/docker-library/official-images/blob/master/library/php).

**No RCE is reproduced.** A version-range match is inventory evidence. A CLI configuration probe is runtime evidence. The business checks cover only the fixture's stated behavior; none proves complete application security, exploitation resistance or incident containment.

## Japan relevance

SakuraShop represents a small Japanese merchant: Japanese UTF-8 catalog/customer data, integer JPY prices with tax already included, and authenticated customer-order controls. The commercial direction is a service that turns upstream signals into evidence-backed draft PRs for such teams, with Japanese/English risk explanations.

[JVN](https://jvn.jp/en/), [JPCERT/CC](https://www.jpcert.or.jp/english/) and [IPA](https://www.ipa.go.jp/en/) are planned regional sources, not implemented integrations or endorsements. JVN currently announces temporary MyJVN/JVN iPedia unavailability starting October 22; collectors need cached replay and an explicit degraded state rather than invented fresh data.

## Run the checks available without PHP or Docker

Requires Node 22+ and Git. No `npm install` is necessary.

```powershell
npm test
npm run assess:baseline
npm run verify:policy
npm run verify:proposed
```

- `npm test`: exercises the detector, real patch application in a temporary directory, unknown inventory, incomplete fixes and duplicate configuration. Passing tests do not make the baseline safe.
- `assess:baseline`: exits 0 only when the expected affected inventory is identified and reports **`security_policy: FAIL`**. Its passing assessment means the demonstration baseline is correctly classified.
- `verify:policy`: exits **1 on the checked-in baseline**, because the actual candidate security policy fails. This is intentional.
- `verify:proposed`: applies the prepared diff in a temporary directory and checks static candidate policy. It leaves repository files unchanged and explicitly reports runtime execution as not run.

The CLI includes a SHA-256 identity of the five verifier files. A future controller must freeze and compare this identity across the job; the presence of these files is not an operating sandbox. The proposed permission contract is in [demo/controller-policy.json](demo/controller-policy.json). Only `Dockerfile`, `composer.json` and `config/security.ini` may change; the candidate must not modify `verification/`, application code or CI.

## Prepare the human-review candidate

Use a disposable Git branch after the baseline has been committed. These are manual commands, not a completed autonomous workflow:

```powershell
git switch -c proofpatch/php-runtime-oct2026
git apply --check demo/proposed-repair.patch
git apply demo/proposed-repair.patch
npm run verify:policy
git diff -- Dockerfile composer.json config/security.ini
```

The patch changes exactly three files: PHP 8.3.35 to the reviewed digest-pinned 8.3.36 image; the Composer PHP floor to `>=8.3.36 <8.4`; and startup upload progress to `0`. Composer constraints alone do not update the running interpreter. `npm test` and `assess:baseline` are baseline-specific; run `verify:policy`, the runtime probe and business checks on the candidate instead.

## Execute candidate PHP checks when a runtime is available

Docker Desktop must have its Linux engine running. **Build only after applying the candidate patch and passing `verify:policy`.** The baseline need not be executed to demonstrate its failing inventory policy.

```powershell
docker build --pull --network none -t sakurashop-review .
$verifierPath = (Resolve-Path ./verification).Path
docker run --rm --network none --read-only --cap-drop ALL --security-opt no-new-privileges --cpus 1 --memory 128m --pids-limit 64 --mount "type=bind,source=$verifierPath,target=/app/verification,readonly" --entrypoint php sakurashop-review /app/verification/runtime-probe.php
docker run --rm --network none --read-only --cap-drop ALL --security-opt no-new-privileges --cpus 1 --memory 128m --pids-limit 64 --mount "type=bind,source=$verifierPath,target=/app/verification,readonly" --entrypoint php sakurashop-review /app/verification/business.php
```

The probe requires actual PHP 8.3.36, effective disabled upload progress, and the fixture's serializer. Business checks verify Japanese text, integer yen totals, anonymous/invalid authentication rejection, cross-customer denial and legitimate own-order success. They exercise domain behavior directly; they are not HTTP pentests. No credentials or Docker socket are mounted, and test containers have no network. Pulling/building the fixed image requires registry access.

With an already installed PHP **8.3.36** interpreter instead:

```powershell
npm run verify:runtime
npm run verify:business
php -c config/security.ini -S 127.0.0.1:8080 -t public public/index.php
```

For a manual candidate storefront preview using Docker, host port publication is restricted to localhost. This preview uses Docker's bridge network; it is separate from the network-disabled verification runs. The fixture itself makes no outgoing requests.

```powershell
docker run --rm --name sakurashop-preview --read-only --cap-drop ALL --security-opt no-new-privileges --cpus 1 --memory 128m --pids-limit 64 -p 127.0.0.1:8080:8080 sakurashop-review
```

Visit `http://127.0.0.1:8080`. In another terminal:

```powershell
curl.exe http://127.0.0.1:8080/api/products
curl.exe -H "Authorization: Bearer sakura-demo-tokyo" http://127.0.0.1:8080/api/orders/order-tokyo-001
curl.exe -H "Authorization: Bearer sakura-demo-osaka" http://127.0.0.1:8080/api/orders/order-tokyo-001
```

Expected results: Japanese catalog JSON; owner order HTTP 200 with total `4800`; other customer HTTP 404. Both public demo tokens are intentionally documented, not secrets or production authentication. No orders can be modified.

## What judges should see in the eventual draft PR

1. Historical vendor signal and source links, labelled replay.
2. Affected runtime declaration and failing baseline inventory policy.
3. Three-file candidate diff, actual model/provider identity if inference was used, and independent reviewer comments.
4. Actual base/head commit IDs, frozen verifier digest, candidate image digest, commands, exit codes and recorded outputs.
5. Observed runtime/configuration and unchanged business controls passing; no claim of exploit reproduction.
6. Draft status, human merge authority and an open deployment/configuration review checklist. Draft publication is distinct from merge recommendation and finding closure.

The publisher must keep GitHub write credentials outside the runner, reuse an existing PR for the same branch, invalidate stale evidence after any candidate/test change, and never auto-merge. No GitHub repository, branch, PR or deployment is created by running the supplied tests.

## Verification status at scaffolding

At scaffolding, all **7 Node tests passed**, baseline assessment correctly identified affected inventory with security policy FAIL, `verify:policy` returned the expected exit 1 on the baseline, and `verify:proposed` passed static checks after actual temporary patch application. `git apply --no-index --check demo/proposed-repair.patch` also passed. These results do not establish runtime behavior.

PHP CLI is absent and Docker's Linux engine is unavailable on the current machine, so PHP business/runtime execution and browser preview are **unverified** until a runtime is supplied. The hosted CI workflow validates baseline classification on main and runs the frozen baseline verifier against candidate PRs. Its candidate checks build and run only the fixed image, use no model key or publication token, and preserve logs as artifacts. CI status must be observed before claiming runtime checks passed.
